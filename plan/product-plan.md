## 1. 产品概述

打造一款以二次元角色为核心的 AI 陪伴 App。用户可以选择并长期陪伴具有独立形象、性格和声音的角色，通过文字及语音交流；角色可结合对话内容呈现简单表情和动作，逐步形成连续、可恢复的互动体验。

产品重点不是单次问答或多个独立会话，而是让用户与一个人物建立持续关系：一个人物只有一条长期存在的逻辑对话，后台自动管理历史归档与记忆，让人物跨时间保持身份和关系连续性。不同人物的数据与记忆彼此隔离。

首版平台与客户端技术选型已有明确决策：Android、iOS；Flutter + Dart。产品能力、服务端技术、商业模式和具体发布节奏仍需逐步验证，不因本计划而视为已定案。

## 2. 产品目标与边界

### 目标

- 提供稳定、易进入的角色聊天体验。
- 让人物身份、唯一持续对话时间线和用户选择能够持久保存并恢复。
- 逐步把角色形象、表情、声音与对话连接起来，形成有表现力的陪伴体验。
- 为人物中心的三层记忆、用户数据所有权/一键导出和多端扩展建立可演进的产品基础。

### 非目标（首版不承诺）

- 不以完整虚拟恋爱、复杂剧情游戏或开放世界作为首版目标。
- 不要求首版支持用户自由制作、发布和交易角色。
- 不要求首版实现完整长期记忆、复杂关系成长或跨会话主动行为。
- 不把实时视频、复杂 3D、精确口型和全功能语音通话列为首版必需能力。
- 不把原生鸿蒙列入首版交付范围；其适配按已接受的 ADR-0002 后续评估。

## 3. 目标用户与核心需求

以下为产品假设，需通过原型体验、用户反馈和实际使用验证，不代表已完成市场调研。

| 用户类型 | 核心需求 | 产品回应 |
| --- | --- | --- |
| 喜欢二次元角色的用户 | 角色形象鲜明，有持续交流的对象 | 角色档案、立绘/模型、性格设定 |
| 希望轻量陪伴的用户 | 随时开始聊天，操作简单 | 直接回到最近会话，低门槛文字交流 |
| 重视沉浸感的用户 | 角色不只是文字，有声音和反馈 | 语音朗读、表情与动作反馈 |
| 希望个性化的用户 | 角色能符合自己的偏好 | 后续提供角色编辑、声音和互动偏好设置 |

## 4. 核心体验与用户路径

### 首次使用

1. 用户打开 App，了解产品并进入角色选择或默认角色体验。
2. 用户选择一个角色，查看角色形象和基本设定。
3. 用户进入聊天，发送第一条消息并收到回复。
4. 对话与角色选择被保存，用户下次打开可继续互动。

### 日常聊天

1. 打开 App 后优先恢复最近使用的人物；该人物始终只有一条持续对话时间线。
2. 用户查看历史消息、输入文字或使用语音入口。
3. AI 回复以流式或适当的渐进方式呈现；用户可取消、重试。
4. 角色根据回复内容呈现适当的表情或动作（能力未接通时使用明确的降级表现）。
5. 切换人物后进入该人物唯一的持续对话时间线；不同人物的原始记录、记忆索引和身份状态完全隔离。

### 角色管理

- 查看角色列表、角色档案和可用形象/声音。
- 每个人物自动拥有且仅拥有一条持续逻辑对话；用户无需创建、切换或管理多个会话。
- 后续支持编辑角色设定、形象、声音和互动偏好。
- 角色删除、重置和数据影响需要有明确提示。

### 语音互动（分阶段实现）

- 语音输入：录音、转写、编辑识别文本、用户确认后发送。
- 语音输出：将回复转换为角色声音并播放。
- 播放中允许停止、切换角色或离开页面；迟到的音频结果不能覆盖当前会话。
- 实时双向语音/通话属于后续能力，不能把界面演示等同于真实通话。

## 5. 产品能力范围

| 能力域 | 基础能力 | 后续增强 |
| --- | --- | --- |
| 角色 | 预置角色、名称、简介、性格设定、形象与声音关联 | 用户创建/编辑、角色导入导出、角色分享 |
| 聊天 | 每个人物一条持续逻辑对话、文字消息、流式回复、取消、失败重试 | 多种聊天模式、消息操作、富媒体互动 |
| 人物时间线与历史 | 每个人物唯一时间线、历史消息持久化、人物隔离、自动归档的基础能力 | 记忆索引检索、历史回溯、跨设备同步 |
| 角色表现 | 静态形象、基础表情/状态切换 | Live2D、更多动作、场景和互动反馈 |
| 语音 | 录音输入、ASR 转写、TTS 朗读的独立能力验证 | 角色音色、情绪表达、连续语音对话 |
| 记忆与个性化 | 人物身份层与近期原始上下文 | 原始记录 / 记忆摘要索引 / 人物身份三层记忆，自动归档、按需回查原始记录、可理解和可管理的长期记忆 |
| 用户数据所有权 | 原始记录和人物资料由用户掌控，支持一键导出当前已有数据 | 全量导出原始记录、归档摘要、记忆索引、人物身份和附件；登录、云端备份/同步、多设备管理 |
| 运营与商业化 | 首版不预设商业模式 | 用量管理、订阅/付费、内容与角色生态 |

表中“基础能力”是产品范围建议，不代表当前仓库已经实现或验收通过。具体实现以代码、测试报告和已合并 PR 为准。

## 6. 阶段路线

阶段表示产品能力的演进顺序，不是人员分工，也不是当前任务状态台账。每个阶段的具体任务通过 GitHub Issue 拆分；跨任务依赖明显时再建立专项协作计划。

### 阶段 0：技术与体验验证

目标：验证客户端基础工程和关键多媒体能力，降低正式开发风险。

- Flutter 工程及 Android 构建、安装和运行流程。
- iOS 工程构建、签名和真机验证。
- 聊天输入、消息展示、人物唯一持续时间线保存与恢复。
- 录音、播放、角色形象/动画分别进行可行性验证。
- 记录真实设备、系统版本、复现步骤、结果和限制。

退出条件：关键技术路径有可复现证据；未验证的平台或能力明确列出，不用模拟结果替代。

### 阶段 1：可用的文字陪伴 MVP

目标：用户能够在 Android/iOS 上选择角色、进行真实文字对话，并在重启后继续使用。

- 完成基础角色列表、角色资料和角色切换。
- 完成聊天主流程、真实模型接入、消息流式展示。
- 支持取消、失败提示、重试和重复请求保护。
- 持久化人物、唯一持续时间线和原始消息；保证人物间数据隔离，并为归档记忆与人物身份版本预留结构。
- 完成最近使用人物恢复、同一条历史时间线查看和基础设置；不提供面向用户的多会话列表/新建会话。
- 完成 Android/iOS 的构建、安装、核心流程验证。

阶段验收以真实模型、真实持久化和目标平台验证为准；模拟回复仅用于开发测试。

### 阶段 2：角色表现与语音体验

目标：让角色从文字对话升级为有形象、有声音的互动对象。

- 接入确定的角色形象资源和基础表情/动作状态。
- 完成 TTS 角色声音播放及停止、切换、失败降级。
- 完成 ASR 录音转写、编辑确认和发送流程。
- 统一文字、形象和声音的状态同步。
- 验证真实设备上的延迟、稳定性、资源占用和体验质量。

Live2D、具体语音模型和服务供应商须经实际验证与决策，不因已有实验 PR 而自动成为最终方案。

### 阶段 3：个性化与持续陪伴

目标：提高角色的可定制程度和跨会话连续性。

- 支持用户编辑角色资料、性格和互动偏好。
- 实现人物中心三层记忆：原始互动记录作为事实层、归档摘要与来源引用作为检索索引层、人物背景/性格/关系/稳定状态作为每轮加载的身份层。
- 自动归档旧时间线并生成可追溯摘要；先检索摘要，必要时展开原始记录。
- 以稳定的人物身份前缀、确定性序列化和动态内容后置提升上下文缓存命中率；缓存效果按模型供应商实测，不承诺无限 Token。
- 记忆更新保留来源、置信度和版本，不能静默覆盖用户明确设定的人物身份。
- 提供用户可理解、可管理的记忆查看、修改和遗忘机制。
- 让用户能够查看、修改或清除影响陪伴体验的个人记忆。
- 逐步加入关系状态、角色主动反馈等能力；每项能力需验证用户价值并提供控制选项。

### 阶段 4：账户、同步与产品化

目标：从单设备可用走向可持续运营的正式产品。

- 按需要引入账户体系和多设备数据同步。
- 建立服务端用量统计、限额、成本控制和异常处理。
- 评估订阅或其他商业模式，明确权益、退款和用量规则。
- 完善内容治理、用户反馈、崩溃监控、隐私说明和数据生命周期管理。
- 建立正式发布、灰度、回滚和版本兼容流程。

### 阶段 5：平台扩展

- 按 ADR-0002 后续评估原生鸿蒙适配。
- 结合用户需求评估桌面端或 Web 端，不预先承诺时间。
- 平台扩展优先复用产品能力和服务接口，平台差异放在适配层处理。

## 7. 体验与质量要求

具体数值阈值应通过目标设备测试和用户体验评估确定，本计划不虚构性能指标。

- **易用性**：首次进入、开始聊天、切换角色和恢复会话路径清晰。
- **响应性**：等待状态明确；支持取消；失败后能恢复操作，不丢失已确认内容。
- **连续性**：应用重启后角色和已保存会话可恢复；角色间数据隔离。
- **一致性**：文字、声音、形象状态对应同一角色和同一轮交互。
- **降级能力**：语音或形象服务不可用时，基础文字聊天仍可用。
- **稳定性**：覆盖弱网、超时、重复请求、快速切换、权限拒绝、后台恢复和存储失败。
- **可维护性**：模型、语音和形象供应商可替换，不让供应商细节渗透整个客户端。
- **可访问性**：关注文字缩放、对比度、触控区域和系统安全区。

## 8. 数据、安全与用户控制

- 用户拥有其人物数据；原始记录、派生记忆和人物身份均属于用户数据，必须提供一键全量导出，不以模型供应商或云服务作为唯一可读载体。
- 导出应使用版本化、公开、可读且供应商无关的格式，并包含原始消息、人物资料、归档摘要、来源索引和附件资源。
- 归档不得删除或覆盖原始记录；删除/重置必须由用户明确触发并说明影响。
- 客户端不得内置模型、语音或对象存储等服务端密钥。
- 真实聊天、录音、用户资料和记忆均按敏感用户数据处理；测试使用合成数据。
- 明确哪些数据保存在设备、哪些上传服务端、用途是什么、保留多久。
- 设计数据删除、账号注销和备份/同步的边界；删除行为应可理解且有适当确认。
- 记忆功能应允许用户查看和管理，不把模型推断当作用户明确提供的事实。
- 对模型生成内容提供必要的安全边界、举报/反馈入口和异常处理。
- 隐私政策、服务条款及适用地区合规要求在正式发布前完成评审。

## 9. 技术与架构约束

### 已确认

- 首版客户端：Flutter + Dart，见 [ADR-0001](../docs/decisions/0001-mobile-stack.md)。
- 首版平台：Android、iOS；原生鸿蒙后续适配，见 [ADR-0002](../docs/decisions/0002-three-platform-scope.md)。
- 服务端密钥由服务端持有，客户端不打包，见 [配置与密钥说明](../docs/guides/configuration.md)。

### 设计方向（待具体方案确认）

- 客户端负责界面、交互、设备能力调用和必要的本地持久化。
- 服务端负责安全调用模型/语音供应商、鉴权、用量控制及需要云端完成的业务。
- 人物、唯一持续时间线、原始记录、归档片段、记忆索引、人物身份版本、生成任务和媒体资源应有清晰的数据边界。
- 内部归档片段、模型请求或供应商 session 不是用户可见的独立聊天；用户视角始终是一人物一条持续对话。
- 每轮上下文由稳定人物身份、近期原始消息、相关记忆摘要及按需展开的原始记录组成。
- 对模型、ASR、TTS、形象渲染等外部能力建立适配接口，便于替换和独立验证。
- 明确本地缓存与云端数据的权威来源、同步冲突和离线行为后，再实现跨设备同步。
- 具体后端语言、框架、数据库、部署方式和通信协议仍待决策；本计划不预设选型。

## 10. 产品效果评估

先建立可观察指标，再根据实际用户基线设定目标值：

- 激活：首次打开后完成角色选择并发送首条消息的比例。
- 使用：活跃用户、会话次数、单次会话时长和回访情况。
- 体验：首字响应时间、回复完成率、取消/失败率、会话恢复成功率。
- 角色：角色选择分布、角色切换率、个性化功能使用情况。
- 多媒体：语音播放成功率、ASR 修改率、形象加载成功率。
- 成本：单次对话及语音交互成本、用户用量分布。
- 质量：崩溃率、关键流程成功率、用户反馈和问题解决时间。

指标采集应遵循数据最小化原则，避免为分析而收集不必要的聊天正文或录音。

## 11. 待产品评审的问题

以下事项未形成正式决策，后续按实际需要通过 Issue 讨论，并在需要时形成 ADR：

- 首版默认入口：直接进入最近使用人物的持续对话，还是先展示当前人物主页？（Issue #14 已确认优先评估 A 角色主页方案，同时保留 B 对照。）
- 首发角色数量、角色内容规范及素材授权方式。
- MVP 是否包含基础 TTS/ASR，还是先完成文字聊天后再单独发布语音能力。
- 形象首版采用静态立绘、序列帧还是 Live2D。
- 三层记忆的归档触发条件、摘要结构、索引召回策略、人物身份更新和缓存优化指标。
- 是否需要登录；本地数据与云端数据的权威关系。
- 后端技术栈、部署区域、模型供应商及成本上限。
- 首版发布地区、内容安全策略、隐私与合规要求。
- 商业模式、用量额度和付费权益。
- 鸿蒙及桌面端的启动条件和优先级。
