## 三、每个 Issue 的工作步骤（批准后可连续执行）

1. 读取最新 main、Issue、相关 ADR/计划、已有 PoC/贡献者 PR；记录复用/不复用理由、当前基线与验收矩阵。
2. 从最新 main 为**该 Issue**建立唯一实施分支；只实现该 Issue 定义的范围，必要时更新对应 plan/ 与文档。已合并前序任务成果成为下一项的基线，不通过复制整条外部 PR 历史复用。
3. 增加正向与负向测试；对人物边界、权限、数据丢失、竞态、重试、导出进行专门回归。必要时包含兼容性/迁移测试，不把 Mock 当作实测。
4. 提交 keeyangyy 的 PR，列出改动、实际执行命令、GitHub Actions 链接/状态、已知限制和未验证内容；检查 diff、敏感信息、授权/许可证与跨人物隐私。
5. 自审以 PR 检查清单/评论记录，不伪装为另一位审核人，也不声称 GitHub 允许作者给自己 APPROVE。仅在必须检查通过且分支保护满足时合并自己的 PR；不绕过审查/CI。
6. 在实际完成且符合 Issue 验收时关闭对应 Issue；记录 commit/PR、CI、关键回归和不足。然后直接进入清单下一项，不再逐项索取用户批准。
7. 全批结束后提交一份集中交付报告：每项状态（完成/部分完成/阻塞）、PR 与合并 SHA、测试/构建证据、真实设备与模型是否验证、遗留风险、下一阶段建议。用户最终一起审阅。

## 四、需显式授权或外部条件的例外

批量计划授权**不等于**授权额外付费、真实凭据、生产上线、资产许可或访问未提供的设备：

- #38/#39：生产部署、第三方账号、付费 API/Token 预算、用户数据外发与服务密钥仍需对应授权。无有效凭据时先实现可验证接口与 Mock，但**不能关闭要求真实联调的验收项**。
- #40：需有可运行的 macOS/Xcode 环境或可用的 GitHub macOS CI runner；环境不可用时记录实际阻塞。
- #41：需可访问的 Android 真机，不能以模拟器假冒设备；没有设备时保持未完成状态。
- #42/#43：麦克风、音频设备、ASR/TTS 凭据和授权音色测试样本；人工听感和跨平台效果不能靠离线模拟证明。
- #44：Live2D/Cubism SDK 的分发/使用许可、合法角色素材及设备测试条件必须满足。未确认时可以完成静态降级与安全接口，但不得把未经授权 Core/模型代码提交仓库。
- 任何新增付费、生产公开部署、数据外传、安全/隐私范围升级、核心产品理念变化或需要推翻已接受 ADR 的决策，都暂停受影响部分并征询授权。不会擅自替用户支付费用或获取第三方个人数据。

## 五、阻塞、质量与集中复核规则

- **质量门槛不可跳过**。如果某项 CI 持续失败、缺少必需评审或真实验收条件，保留开放 PR/Issue、明确阻塞原因；不能为了凑齐 11 项把失败标记为完成。
- 依赖受阻时，不修改其下游的正式生产依赖来假装可用；可做独立的文档、Mock 验证或无依赖任务，明确区别“代码已写”和“端到端已验收”。
- GitHub 是异步事实台账：PR、Actions、Issue 上始终保留进度和可审阅证据；**本批不要求每完成一项就在聊天中等待确认**，最终汇总给用户。
- 本文件授权范围只涵盖现存 11 项 Issue；账号系统、云同步、原生鸿蒙、正式发布等未拆成可执行 Issue 的方向仍属于后续路线，不默认纳入本批。
- 当前 ChatGPT 会话不保证跨会话或离线持续执行；代码执行须在实际可用的交互/工作会话中进行，不将“提交计划”冒充“后台已启动”。若工作需要后续会话继续，可直接按本计划与 GitHub 状态续跑，无需重复批准已确认的范围。
