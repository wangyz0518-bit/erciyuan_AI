# Issue #43：设备端可编辑 ASR / 系统 TTS 基础链路

日期：2026-11-19。与正式持续聊天 UI 和 Issue #42 音频生命周期组合实施；此提交不依赖付费云端供应商。

## 技术边界和来源

- 参考 PR #18/#19 的语音能力对比，PR #21 的“文字保存与声音重试分离”、PR #22 的取消/迟到分离；不移植依赖旧 PoC 的整包分支。
- 本阶段采用 speech_to_text 7.5.0（BSD-3-Clause）和 flutter_tts 4.2.5（MIT）；许可证来源为各自 pub.dev license 页面。正式分发仍需保留完整 OSS notices 并复查传递依赖。
- ASR 默认只请求系统 **onDevice: true**，没有可用设备端识别引擎时提示用户改为手动输入，不私自回退到在线供应商。麦克风/识别权限由 OS 弹窗授权；操作由用户主动触发。
- 识别结果仅存页面内存，并展示“填入草稿”按钮；之后仍须用户自行编辑检查并按“发送”。不复用音频临时文件、不自动写 SQLite，不产生第二条会话。
- TTS 使用平台默认系统语音，用户显式点击已有完整回复的“系统朗读”，不是角色专属音色，也不是 CosyVoice；系统语音引擎可能需要网络，不承诺端侧或不传输文本。
- 角色切换、页面退出、前后台暂停时停止识别/朗读并使迟到回调失效。无需收集/提交私人录音、供应商密钥。
- 对真实角色音色绑定、供应商音色克隆、声音授权/删除、流式 PCM 跨平台、多设备实际听感与时延仍需独立的授权和验收证据，因此不能用此基础能力关闭 #43。

## 自动测试与未验证

- 基于可注入的假 ASR/TTS 测试转写不自动发送、迟到结果丢弃、离线不可用、停止播放、销毁清理。
- GitHub CI 需执行 Flutter format/analyze/test、Android APK 和模拟器；iOS 由 #40 实际 macOS/Xcode 作业验证。
- 设备端识别的可用性由安装的系统语言包/语音服务决定；必须对 Android/iOS 真机分别测权限、中文准确率、听感及系统引擎网络策略。
