# 手机端框架选型复核与建议（三端需求版）

> 日期：2026-11-11  
> 状态：供团队审阅的选型建议，尚非最终技术定案。  
> 目的：结合已确认的产品架构，复核《移动端技术方案调研》的结论，明确首选方向、备选方案及验证条件。  
> 范围：手机端框架；不新增产品功能，不编写产品代码，不替代原调研报告。  
> 关联工作线：A 手机界面与交互、B 角色与对话核心、C 形象制作与驱动、D 声音处理。验证负责人待团队分配。

## 1. 给非技术成员的结论

建议将 **普通 uni-app + Vue 3 + TypeScript** 作为手机端首选技术方向，将 **Flutter + 鸿蒙适配方案** 作为重点备选。

这个判断基于当前项目的优先级：苹果、安卓、原生鸿蒙均为目标；先完成聊天、角色管理和记录保存，再增加语音与动态形象。我们希望减少重复开发，并在初期就检查三端是否可行。

这不是“uni-app 已被证明最好”的结论。尚未在本项目进行三端构建、性能、数据库、录音播放或角色动画验证；本次文档整理与上传也不表示框架已获最终确认。后续应先用小样验证关键能力，再大规模开发页面。

几个名称分别表示：

| 名称 | 在项目中的含义 |
| --- | --- |
| uni-app | 帮助共用代码、开发不同手机系统应用的框架 |
| Vue 3 | 在框架内组织页面和交互的方式 |
| TypeScript | 编写角色、聊天等程序逻辑的语言 |
| Flutter | 另一套手机应用框架，主要使用 Dart 语言 |
| 鸿蒙适配方案 | 让框架及相关组件能够构建、运行于原生鸿蒙的额外实现 |
| 验证小样（PoC） | 功能很少的测试程序，用于确认关键技术是否可用 |

## 2. 本次比较使用的需求前提

以下架构已在当前讨论中确认，框架选型应服从这些前提：

1. 手机负责角色展示、输入、消息展示、录音播放及本地记录。
2. 一个统一后台负责整理角色设定和近期对话、调用外部模型及处理错误。
3. 苹果、安卓、原生鸿蒙客户端共用同一个后台。
4. 第一版角色设定与聊天记录主要保存在手机；我们的后台不承担长期聊天存储。
5. 外部 AI 服务提供对话能力，后续再接入语音识别与语音合成。
6. 形象、声音、聊天和数据保存分别组织，便于逐步扩展。
7. 第一版先不建设账号同步、长期记忆、付费系统或手机本地大模型推理。

“鸿蒙支持”指原生鸿蒙应用，不以华为设备能够运行安卓 APK 作为验收依据。三端从选型和初期验证阶段共同考虑；具体发布节奏另行安排，不在本次复核中擅自删除或推迟鸿蒙目标。

当前需求没有确定必须首版完成复杂三维角色、精细嘴型或可随时打断的实时语音通话。也不能把这些未来能力视为框架自带、无需适配。

## 3. 与伙伴报告的主要差异

复核对象为提交 [a5ca800](https://github.com/wangyz0518-bit/erciyuan_AI/commit/a5ca800cfb46d4bfc9e81919cdb76e38a6cb33fd) 中的 [《移动端技术方案调研》](https://github.com/wangyz0518-bit/erciyuan_AI/blob/a5ca800cfb46d4bfc9e81919cdb76e38a6cb33fd/docs/%E8%B0%83%E7%A0%94/%E7%A7%BB%E5%8A%A8%E7%AB%AF%E6%8A%80%E6%9C%AF%E6%96%B9%E6%A1%88%E8%B0%83%E7%A0%94.md)。

原报告明确把鸿蒙排除在第一阶段目标之外，并在项目分析中将其列为未来可能项。因此，其 Flutter 首选结论主要面向 Android/iOS 优先的路线。

| 比较项 | 伙伴报告使用的前提 | 本次复核使用的前提 |
| --- | --- | --- |
| 平台目标 | Android/iOS 优先，鸿蒙后续评估 | 三端均为目标，初期共同检查可行性 |
| Flutter 的主要吸引力 | 共享双端界面、定制视觉表现 | 保留这些优势，同时计入鸿蒙适配负担 |
| uni-app | 列入平台矩阵，未进入候选评分表 | 作为符合当前功能范围的重点候选 |
| 角色动画 | 后续验证 Live2D 等方案 | 大规模页面开发前验证一个代表性目标效果 |
| 决策依据 | 生态资料、项目案例及定性评分 | 相同需求下的组件支持、实际验证和维护责任 |

两份建议的分歧首先来自需求权重不同，并不等于某个框架在所有场景下更好。

## 4. 原报告中建议采纳的内容

- **界面与业务分开。** 角色、会话、消息的规则不应全部写在页面中。这样可减少后续更换界面实现时的改动，但不保证跨语言迁移零重写。
- **模型服务通过后台接入。** 手机负责采集、播放和交互，与已确认架构一致。
- **统一处理失败与状态。** 请求失败、角色切换、重复操作、声音停止、记录恢复需要有明确行为。
- **用真机验证关键能力。** 动画、音频、存储、启动和持续使用表现应由实际结果判断。
- **第一阶段不增加 Go/Rust 本地核心。** 当前没有已确认的离线运算需求，不必额外增加语言、跨语言连接和构建工作。

原报告中的流式回复、推送等建议属于可讨论的扩展项，本次复核不将其自动加入第一版交付范围。

## 5. 原报告尚不足以支持的结论

### 5.1 尚未形成针对三端需求的完整候选比较

uni-app 出现在平台矩阵中，但没有进入后续评分表；uni-app x 未展开。因此，现有评分不能证明 Flutter 已优于这两种方案。

评分、项目数量、Stars 和下载量可以辅助了解生态，不能直接证明我们的聊天、数据库、动画和音频组合能够运行。本次没有逐个复核报告列举的开源应用，也没有验证其统计数据，不以这些数字作为决定性依据。

### 5.2 页面动效能力不等于角色动画已经解决

Flutter 的渲染体系有利于自定义界面和动效，但 Live2D 的模型加载、动作、嘴型和各平台接入仍需单独实现或引入组件。[Flutter 架构说明](https://docs.flutter.dev/resources/architectural-overview)

Live2D 官方平台支持表区分不同 SDK 路线；Unity 路线中的鸿蒙支持注明需要团结引擎。不能把 SDK 的某条支持路线直接等同于任意应用框架已经可用。[Live2D 平台说明](https://docs.live2d.com/en/cubism-sdk-manual/platform/)

### 5.3 React Native + Expo 不能直接视为完整鸿蒙方案

Expo 提供 React Native 开发与构建工具，其常规 CLI 平台参数为 iOS、Android、Web。鸿蒙需要另外检查 RNOH、原生组件和构建流程；不能从“React Native 存在鸿蒙适配”推出“所选 Expo 功能可以直接用于鸿蒙”。这并非断言所有 Expo 能力均无法适配。[Expo CLI](https://docs.expo.dev/more/expo-cli/)、[华为跨平台方案](https://developer.huawei.com/consumer/cn/doc/guidebook/solution-0000002784651007/)

### 5.4 Flutter 鸿蒙路线应认真评估，不能笼统排除

华为官方列出了 Flutter 鸿蒙适配、插件扩展及三方库适配路径。此前仅以“依赖适配分支”解释风险不够充分。

正确的检查对象是：选定版本下，数据库、录音、播放、文件和角色展示组件能否一起工作；出现问题由谁维护。React Native 和 uni-app 同样需要做组件层面的检查。[华为跨平台方案](https://developer.huawei.com/consumer/cn/doc/guidebook/solution-0000002784651007/)

## 6. 当前推荐及取舍

| 方案 | 当前定位 | 理由和限制 |
| --- | --- | --- |
| 普通 uni-app + Vue 3 + TypeScript | 首选验证方向 | 当前主体是聊天、角色设置及记录管理，有三端开发路径；仍须核查数据库、音频和动画组件 |
| Flutter + 鸿蒙适配方案 | 重点备选 | 自定义视觉表现有吸引力；需要落实鸿蒙版本和插件组合的维护 |
| uni-app x | 保留观察候选 | 有三端及原生渲染路线；需确定模式、系统版本与插件兼容，不默认与普通 uni-app 可互换 |
| React Native + RNOH | 团队技能匹配时再重点评估 | 若成员有成熟 React Native/鸿蒙经验，可能提升实施效率；Expo 能力仍需单独检查 |
| 三端分别原生开发 | 当前不优先 | 能直接针对平台优化，但维护多套客户端的工作较多 |
| Unity/团结路线 | 复杂角色互动成为核心时重新评估 | 图形和角色互动定位不同，不因未来可能加动画就立即替换整个应用主体 |

uni-app 对原生鸿蒙提供明确开发路径，要求使用 Vue 3；框架支持平台不代表全部插件自动兼容。[uni-app 鸿蒙说明](https://uniapp.dcloud.net.cn/tutorial/harmony/intro.html)

uni-app x 的不同模式存在具体限制。例如当前蒸汽模式要求 iOS 15 及以上、鸿蒙 API 20/鸿蒙 6.0 及以上等，不能将这些条件泛化到所有模式，也不能不核对目标设备就选定。[uni-app x 模式说明](https://doc.dcloud.net.cn/uni-app-x/app-vapor.html)

推荐 uni-app 是基于本项目的范围与维护投入判断，尚非性能或成本实测结论。若团队已有成熟 Flutter 经验并能承担鸿蒙适配，该条件足以重新评估候选顺序；成员背景目前未核实，不按账号自动推断。

## 7. 开始产品开发前的验证条件

用户批准开始技术验证后，优先用 uni-app 完成小样，不必同时制作两套完整产品。Flutter 保留作备选，在首选出现关键问题或需要对照时再开展对应验证。

| 验证项 | 三端分别检查的内容 | 结果记录要求 |
| --- | --- | --- |
| 构建安装 | 生成原生平台安装包，安装和启动 | 记录框架、SDK、设备、系统和构建版本 |
| 聊天与输入 | 中文输入、键盘遮挡、消息滚动、后台请求 | 使用相同操作脚本；区分真实回复与模拟回复 |
| 本地数据 | 保存角色与记录，改名、切换角色、关闭后恢复 | 记录数据库实现；检查串记录、重复消息和未完成状态 |
| 短语音 | 授权、拒绝授权、录音、播放、切换角色停止声音 | 检查格式兼容和错误恢复；不冒充实时通话验证 |
| 目标角色效果 | 选用有使用权限的代表性素材；若目标是 Live2D 就验证实际模型 | 观察动画与聊天同时运行时的流畅度、内存和资源占用 |
| 网络与恢复 | 断网、超时、重试、重新进入页面 | 保留输入，等待状态结束，避免重复保存 |

普通 uni-app 录音文档列有鸿蒙兼容说明，但 App 对部分能力存在限制，例如录音分片回调不受支持。基础录音不能代替实时语音方案。[录音接口说明](https://uniapp.dcloud.net.cn/api/media/record-manager.html)

验证前还需明确目标设备、最低系统版本、可接受的响应与动画表现，以及成员可承担的维护工作。当前不承诺未经测试的帧率、延迟、包体积、开发周期或费用。

没有设备、签名或构建环境的平台标记为“尚未验证”；不能因为另外两个平台运行成功就宣布三端通过。

## 8. 定案与调整条件

满足以下条件后，再将首选升级为正式技术定案：

1. 三端必要功能的小样通过，并保存可重复构建的版本组合。
2. 数据保存、录音播放及目标形象路线均有可用实现。
3. 平台特有代码集中在适配部分，团队能够理解并维护。
4. 所用插件和素材的使用条件、源码可获得性及维护责任已检查。
5. 团队审阅验证结果，确认第一版范围及剩余限制。

以下情况出现时，应重新比较 Flutter 或其他方案，而不是继续堆补丁：

- 关键功能缺少可维护的三端实现。
- 目标角色动画与聊天同屏时无法达到预先约定的体验要求。
- 所需原生适配已使共用代码的收益明显下降。
- 团队技能或产品定位发生实质变化。

整体架构与手机框架分开管理：即使后来更换客户端框架，统一后台的职责和接口仍可尽量保留；客户端界面、插件及部分业务代码可能仍需迁移。
