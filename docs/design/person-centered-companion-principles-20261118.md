# 人物中心的持续陪伴与记忆原则

> 状态：产品原则已由项目发起人确认；具体技术架构待 Issue #34 评审
> 日期：2026-11-18
> 关联：[#14 主界面原型](https://github.com/wangyz0518-bit/erciyuan_AI/issues/14)、[#34 正式 Flutter 架构](https://github.com/wangyz0518-bit/erciyuan_AI/issues/34)、[#36 本地数据层](https://github.com/wangyz0518-bit/erciyuan_AI/issues/36)

## 1. 核心理念

本产品以**人物身份（Character / Persona）**为核心，而不是以一次会话（Conversation / Session）为核心。

- 一个用户可以拥有多个不同人物。
- 每个人物只有一条持续存在的逻辑对话时间线，承载与该人物的全部历史。
- 用户不需要创建、切换或管理多个聊天会话；后台自动完成上下文窗口管理、历史归档和记忆检索。
- 切换人物意味着切换到另一个独立的人物对象，而不是切换同一 Agent 下的会话。
- 每个人物拥有独立的原始记录、记忆索引和身份状态；人物之间不共享对话或记忆。
- 数据属于用户。原始记录与由其派生的记忆、人物状态都应可由用户一键完整导出，避免被某个模型供应商或服务端实现锁定。

这是一项产品和系统设计原则，不是对无限 Token、无限模型上下文或某个模型供应商能力的承诺。

## 2. 术语和边界

| 概念 | 定义 | 是否向用户呈现 |
|---|---|---|
| 人物 / Character | 持续存在的角色身份、设定、关系和独立数据边界 | 是 |
| 持续对话 / Character Timeline | 某个人物唯一的逻辑对话，跨时间持续追加 | 是，作为一条连续时间线 |
| 原始记录 / Raw Events | 用户与人物的原始消息及相关交互记录，是事实来源 | 可查看、可导出 |
| 归档片段 / Archive Segment | 后台按时间、长度或主题对原始时间线做的内部组织单元 | 默认不作为新会话呈现 |
| 记忆索引 / Memory Index | 从归档片段生成的摘要、主题、实体和来源引用 | 可在后续记忆管理能力中查看 |
| 人物身份层 / Persona Identity | 人物背景、性格、表达风格、关系和稳定状态 | 人物资料可查看/编辑 |
| 技术请求 / Request | 一次模型调用、流式连接或任务执行的技术标识 | 不作为用户聊天边界 |

实现可以使用内部 archive、context window、request 或 provider session 等技术结构，但这些结构不得变成用户需要管理的多个对话。

## 3. 三层记忆结构

### 第一层：原始会话数据（事实层）

保存完整、可追溯的原始互动记录，是整个记忆系统的底层事实来源。

建议至少保留：
- 稳定的事件 ID、人物 ID、用户 ID、时间戳和发言方；
- 原始文本、附件/音频/图片等资源引用及必要元数据；
- 事件类型、来源、版本和必要的校验信息；
- 记录之间的顺序关系，以及归档/摘要引用到的原始事件范围。

归档和摘要不能删除或覆盖原始记录。纠错、用户编辑和删除应有明确的数据生命周期语义，不能由摘要任务静默改写事实层。

### 第二层：记忆归纳与索引（检索层）

后台把持续对话中的历史内容按时间、长度或语义主题整理为归档片段，并生成对应的摘要和索引。

一个记忆条目应能回答：
- 总结了什么；
- 涉及哪个人物、主题、时间范围或关系；
- 对应哪些原始事件/归档片段；
- 由哪个模型/规则和版本生成；
- 生成时间、置信度、来源和后续修订情况。

检索时优先读取相关摘要和索引；只有当当前问题需要具体原话、细节、时间顺序或证据时，再展开读取对应原始记录。摘要必须保留来源引用，避免变成不可追溯的“模型印象”。

### 第三层：人物身份（持续身份层）

保存每轮对话都需要加载的稳定人物上下文，包括：
- 人物背景、身份设定和核心经历；
- 性格特征、价值偏好、表达风格和互动边界；
- 与用户的关系定位和已确认的关系状态；
- 经长期互动验证的稳定事实与偏好；
- 当前阶段的必要状态。

身份层必须区分：
1. 用户/创作者明确设定的基础身份；
2. 从原始记录和记忆索引归纳出的动态状态；
3. 模型推断但尚未确认的候选信息。

动态归纳不能静默覆盖用户明确设定的基础身份。重要变化应保留来源、置信度、版本和必要的用户确认/编辑入口。

## 4. 自动归档与记忆更新流程

传统上下文压缩在这里转化为后台归档，而不是把旧消息丢弃或另开一个用户可见会话。

1. 新消息按时间顺序追加到人物唯一的原始时间线。
2. 当达到长度、时间或语义边界时，后台创建归档片段；触发条件由后续架构与成本评估确定。
3. 为归档片段生成摘要、主题和来源索引，明确引用原始事件 ID。
4. 对摘要执行完整性和来源校验；失败时保留原始记录并允许重试。
5. 从高置信度、可追溯的长期信息中提出人物身份层更新；不得把一次性情绪或未经确认的猜测直接写成稳定人格。
6. 更新索引和人物身份版本，记录生成模型、规则版本和来源。
7. 未来每轮对话仍属于同一人物时间线；归档仅改变后台组织方式，不改变用户对“同一个人物一直记得”的体验。

归档必须幂等、可重试、可审计；原始记录是最终可回查依据，摘要和人物状态应可从原始记录重新构建或校正。

## 5. 每轮上下文装配与高缓存率

“无限上下文”是持续陪伴的产品体验目标，技术上仍受模型上下文窗口、延迟和成本限制。系统通过分层检索与上下文装配，让人物能在长时间跨度内保持连续性。

建议每轮上下文由以下部分组成：

1. 稳定的人物身份前缀：人物基础身份、性格、表达风格和边界；
2. 当前对话最近的原始消息：保证短期语境和自然接续；
3. 从记忆索引检索的相关摘要：按当前问题召回必要的历史事实；
4. 按需展开的原始记录：当摘要不足以回答时，读取来源记录；
5. 当前请求和工具结果：仅包含本轮动态信息。

为提高模型前缀缓存命中率：
- 人物身份层采用稳定、可版本化、确定性序列化的前缀；
- 不把时间戳、随机 ID 等易变字段混入稳定前缀；
- 固定系统提示、人物身份和输出约束的顺序与格式；
- 将本轮变化的检索摘要和近期消息放在稳定前缀之后；
- 记录缓存命中率、输入 Token、检索延迟和回答质量，按供应商实际缓存规则验证。

缓存命中率是优化目标，不是所有模型服务都保证的结果。切换模型供应商时必须重新验证缓存语义和效果。

## 6. 人物隔离与用户数据所有权

### 人物隔离

- 每个人物有独立的逻辑时间线、原始记录、记忆索引和身份状态。
- 任意两个不同人物之间不得默认共享聊天正文、摘要、偏好或推断出的关系信息。
- 数据访问、缓存键、检索范围和导出范围都必须包含用户与人物边界。
- 用户级设置如语言/字体偏好是否跨人物共享，应与人物记忆严格分开并由用户控制。

### 用户拥有数据

用户应能一键导出自己的全部人物数据，而不只是导出当前可见聊天窗口。导出范围至少应覆盖：
- 全部人物身份设定和可编辑资料；
- 每个人物完整的原始对话时间线及必要元数据；
- 归档片段、记忆摘要、索引条目及其原始来源引用；
- 人物身份层的动态状态、版本、来源和确认状态；
- 用户拥有的附件/媒体文件或可校验的资源引用；
- 数据格式版本、导出时间和完整性清单。

导出格式应版本化、公开、可读且不依赖单一模型供应商。建议以 JSON/JSONL 与附件目录打包；具体格式、加密和恢复方案由后续任务确定。云同步或更换模型服务不得改变用户对数据的所有权。

## 7. 对界面设计的约束

- 首页以人物为入口；A 方案优先展示人物身份，主操作为“继续与 TA 对话”。
- B 方案可以直接打开最近使用人物的时间线，但它仍是同一人物唯一的持续对话。
- 人物切换是切换独立人物对象，不是切换同一人物的聊天会话。
- 不提供“新建会话”“会话列表”“切换会话”等用户操作。
- 历史以同一条时间线浏览；归档是后台管理，不把归档片段伪装成新会话。
- 在“我的/数据管理”提供一键导出所有人物数据的入口。
- 原型可以模拟数据保存和 JSON 导出，但必须明确标注合成数据及非正式存储。

## 8. 分阶段落地边界

| 任务 | 必须落实的内容 |
|---|---|
| #14 | A/B 原型围绕人物和唯一持续时间线设计；展示人物切换、连续历史和数据导出入口 |
| #34 | 正式架构定义人物、持续时间线、原始记录、记忆索引、人物身份和上下文装配边界 |
| #36 | 本地数据按人物隔离；每人物一条逻辑时间线；数据结构可导出；不建面向用户的多会话模型 |
| #37 | 正式 UI 不出现会话列表/新建会话；提供人物入口、持续时间线和数据导出入口 |
| #38/#39 | 服务端与模型上下文遵循人物隔离、来源追溯和分层上下文装配 |
| 后续记忆任务 | 实现自动归档、摘要索引、人物身份更新、相关记忆召回和缓存率优化 |

本文件定义产品原则和设计约束，不代表三层记忆、自动归档、模型缓存或全量导出已经实现。每项能力必须以对应 Issue、代码和验证证据为准。
