# ADR-0002 三端范围确认

- 状态：提议，待团队确认
- 日期：2026-11-11
- 决策者：待定（A/B/C/D 工作线共同确认）

## 背景

《手机端框架选型复核与建议（三端需求版）》把 Android、iOS、原生鸿蒙都列为首版目标，并明确“鸿蒙支持”指原生鸿蒙应用，不以安卓 APK 在华为设备上运行为验收依据。

这与 ADR-0001 的前提不同：ADR-0001 把鸿蒙视为未来可能项，主要按 Android/iOS 比较，因此得出 Flutter 优先的结论。

## 选项

1. **三端都做**：Android、iOS、原生鸿蒙同步纳入首版。
   - 优点：一次覆盖主要市场，避免后期返工。
   - 代价：框架选择、构建链、真机验证和人力成本都增加。
2. **Android/iOS 优先，鸿蒙后续**：先把双端跑通，再单独适配鸿蒙。
   - 优点：首版风险低，交付快。
   - 代价：如果架构没有为鸿蒙留余地，后续可能重写 UI 层。
3. **Android 优先**：iOS 和鸿蒙都后置。
   - 优点：最省资源。
   - 代价：与当前产品目标不一致，除非团队明确缩减范围。

## 决定

待团队确认。确认前，ADR-0001 的 Flutter 首选结论只适用于 Android/iOS 优先的前提，不能直接作为三端方案。

## 后果

- 若确认三端，需要重新评估候选框架，至少包括 uni-app、Flutter + 鸿蒙适配、RNOH、Kuikly 和原生 ArkTS。
- 需要补充鸿蒙侧 PoC：构建、录音播放、本地存储、形象渲染、包体积和真机性能。
- 接口契约需要明确三端共用的后台边界，客户端差异不应改变接口语义。
- 确认后更新 ADR-0001 的状态：保留历史结论，标注前提变化或被取代。
