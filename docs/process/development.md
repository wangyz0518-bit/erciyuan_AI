# 开发与评审流程

本文补充日常任务从 Issue 到 PR 合并的操作约定。开放式协作原则见 [collaboration.md](collaboration.md)；仓库入口见 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 1. Issue 与任务

需要产生代码、文档或可验收产物的工作，优先建立或复用 GitHub Issue。Issue 至少说明：

- **目的**：解决什么问题。
- **交付内容**：预期产出什么。
- **依赖与风险**：依赖哪些任务、接口或外部条件；没有可留空。
- **验收条件**：如何检查结果。

Issue 不必预先指定负责人或参与者。任何成员都可以处理任何人的 Issue；若已有成员在推进，应先在 Issue 中协调范围。Issue 创建者与实现者可以不同。

## 2. 分支

`main` 保存已经评审并确认可作为共同基线的成果。每项工作使用独立分支，例如：

- `feat/<scope>-<topic>`
- `fix/<scope>-<topic>`
- `docs/<topic>`
- `test/<scope>-<topic>`

默认从最新 `main` 开始。只有存在明确依赖时才从其他工作分支开始，并在 PR 中说明前置 PR 及本 PR 的增量范围。不要为了方便合并，把多个独立任务长期串成一条分支链。

不得强制推送覆盖他人分支或公共分支。遇到冲突先核对双方意图，不直接覆盖他人的修改。

## 3. Pull Request 状态

PR 是可独立审阅的变更单元，不要求一次完成整个 Issue。

### Draft

适用于仍在实现、需要讨论设计、验证证据不足或依赖尚未稳定的变更。Draft 可用于尽早共享进展，但不应被视为可合并。

### Ready for review

转为 Ready 前应确认：

- 目标和修改范围明确；
- 自审及相关测试/检查已完成；
- 文档、接口和索引已同步；
- 未验证事项、已知问题和剩余工作明确列出；
- PR 描述能让审阅者理解本次增量。

PR 描述至少说明：做了什么、为什么修改、影响范围、如何验证、哪些没有验证，以及依赖的 Issue/PR。

如果 PR 基于尚未合并的其他 PR，必须明确标注前置 PR，并提供本 PR 增量的 commit 或 compare 范围，避免重复评审前置变更。

## 4. 作者自审与合并规则

### 自审要求

PR 作者必须对自己提交的完整差异进行自审，并在 PR 描述或评论中留下记录。自审至少检查：

- 变更文件和 diff 是否都属于当前 Issue；是否夹带无关内容；
- 相关调用方、数据模型、接口、文档和索引是否同步；
- 是否检查已有 Issue/PR 和可复用成果；是否错误复制其他分支的历史提交；
- 是否引入密钥、令牌、真实用户数据、私人录音或未经授权素材；
- 相关单元、Widget、集成、平台或文档检查是否实际运行；
- 所有必需 CI 是否完成；失败、未验证和模拟结果是否如实标记；
- 是否存在未处理的阻塞 Review 意见或兼容性问题。

GitHub 不允许 PR 作者批准自己的 PR。这里要求的是作者完成并记录实质性自审，不要求作者向自己提交 GitHub formal approval。

### 合并权限与条件

- **默认只合并自己提交的 PR。** 可以处理任何成员创建的 Issue，但不因此获得合并该成员 PR 的默认权限。
- 对其他成员的 PR，可以审阅、评论和协助；如需实现同一 Issue，可协调后从最新 `main` 建立自己的分支，提交自己的 PR，并注明相关设计/代码来源。不要修改、覆盖或关闭他人的 PR/分支。
- 只有项目发起人明确授权时，才例外合并其他成员的 PR。
- 自己提交的 PR 完成自审后，只有同时满足以下条件才可合并：
  - 目标分支正确，PR 与 Issue 范围一致；
  - PR 可合并，无未解决冲突；
  - 所有必需 CI/检查通过；不适用的检查需说明原因；
  - 无未处理的阻塞 Review 意见；
  - 文档、接口、数据迁移和验收证据已同步；
  - Issue 的验收条件已满足，未验证事项没有被伪装成通过。
- 如果仓库分支保护要求额外审批或其他条件，不得绕过保护；请求所需审阅或保持 PR 未合并。不得用管理员权限或其他方式绕过检查。

### 重要变更

涉及公共接口、数据模型、架构或兼容性的重要变更，应先在 Issue 中讨论影响范围并取得项目发起人/相关参与者对方案的确认。可以邀请其他参与者独立 Review；作者自审不能替代产品决策确认或仓库强制的审批规则。

## 5. 验收证据

描述验证结果时统一区分：

| 状态 | 含义 |
| --- | --- |
| 通过 | 已按明确步骤实际验证 |
| 未验证 | 当前没有足够条件验证 |
| 失败 | 已执行并失败 |
| 模拟 | 使用 Mock、占位或离线替代，不能当作真实能力 |

“通过”应尽可能说明运行环境、操作步骤和实际结果。模拟验证不能替代真实服务、真机或用户体验验收。

性能数据应说明设备/环境、样本量、测量边界及是否使用热缓存或模拟条件；小样本结果不能写成产品级承诺。人工听感、视觉效果等主观验收，应明确由谁、基于哪些样本确认，不能用自动测试代替。

## 6. 变更原则

- PR 尽量围绕一个主题，避免夹带无关文档整理。
- 不直接覆盖他人的修改；遇到冲突先核对双方意图。
- 不强制推送公共分支。
- 不把“计划完成”写成“功能完成”。
- 不提交密钥、真实用户数据、私人录音或本机敏感文件。
