# 开发协作规范

本文件定义日常任务从提出到合并的最小流程。产品规划、技术决策和具体接口不在这里重复。

## 1. 任务

需要产生代码、文档或可验收产物的工作，先建立 GitHub Issue；小型修复也至少在 PR 中说明目的和验收方式。

Issue 至少说明：
- 目的
- 范围
- 依赖
- 验收条件

不把 Issue 写成实现方案；实现细节在工作过程中确定并记录。

## 2. 分支

`main` 只保存已经评审并确认可以作为共同基线的成果。

每项工作使用独立分支：
- `feat/<scope>-<topic>`
- `fix/<scope>-<topic>`
- `docs/<topic>`
- `test/<scope>-<topic>`

默认从最新 `main` 开始。只有存在明确依赖时才从其他工作分支开始，并在 PR 中写明：

> 基于 PR #N；本 PR 的增量为……

不要为了“方便合并”把多个独立任务长期串成一条分支链。

## 3. Pull Request

PR 是可审阅的变更单元，不要求一次完成整个 Issue。

### Draft

实现中、证据不足或明确需要讨论时使用 Draft。

### Ready for review

达到以下条件后再转 Ready：
- 目标和范围明确；
- 自检和相关测试已完成；
- 文档/接口已同步；
- 剩余问题已经明确列出；
- Reviewer 可以只根据 PR 描述和代码开始评审。

PR 描述至少包含：
1. 做了什么；
2. 为什么这样做；
3. 影响什么；
4. 如何验证；
5. 哪些没有验证；
6. 依赖哪些 PR/Issue。

如果 PR 基于未合并 PR，必须提供“本 PR 增量”对应的 commit 或 compare 范围，避免 Reviewer 把前置工作重复评审。

## 4. Review 与合并

正常变更至少经过一名其他成员 Review；接口、数据模型、架构和跨工作线变更需要相关负责人参与。

Review 结果只分三类：
- **Approve**：可以合并；
- **Request changes**：存在必须处理的问题；
- **Comment**：建议或讨论，不阻塞合并。

没有必要为了“全部 PR 都有 Review”而机械审批；Review 的对象是当前 PR 的实际增量。

合并前确认：
- CI / 必需检查全部通过；
- 所需 Review 已通过；
- 没有未处理的阻塞意见；
- PR 仍符合目标 Issue。

## 5. 验收证据

统一使用四种状态：

| 状态 | 含义 |
| --- | --- |
| 通过 | 已按明确步骤实际验证 |
| 未验证 | 当前没有足够条件验证 |
| 失败 | 已执行并失败 |
| 模拟 | 使用 Mock、占位或离线替代，不能当作真实能力 |

“通过”必须能说明环境、步骤和结果。

性能数字必须同时说明样本、连接状态和测量边界；小样本不得写成产品级承诺。

人工听感、视觉效果等主观验收必须明确“谁在什么样本上确认”，不能用自动测试代替。

## 6. 文档

文档按职责归类：
- `docs/research/`：事实、调研和候选方案；
- `docs/decisions/`：已经确认的取舍及理由；
- `docs/guides/`：开发、配置和排障；
- `docs/接口/`：接口契约及示例；
- `docs/reports/`：实际验收和测试报告；
- `docs/process/`：本项目协作规则；
- `planning/`：产品/阶段计划及其原始文档，不与实施状态混用。

同一规则只保留一个权威位置，其他地方链接过去。

## 7. 变更原则

- 不直接覆盖历史决策和验收记录。
- 被取代的方案保留，并标明取代关系。
- 不为了满足目录结构创建空文档。
- 不把“计划完成”写成“功能完成”。
- 不提交密钥、真实用户数据、私人录音或本机生成的敏感文件。
