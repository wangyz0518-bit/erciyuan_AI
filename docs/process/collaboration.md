# 开放式协作

## 协作模式

- 项目采用开放式协作，不预设固定工作线、模块负责人或成员分工。
- 成员根据具体任务参与；一项任务可以由一人完成，也可以由多人共同推进。
- 不以历史计划中的工作线划分限制成员参与范围。

## 任务协作

- GitHub Issue 是具体任务、问题讨论和验收条件的主要载体。
- 任务描述应说明目的、交付内容和可检查的验收条件；存在依赖或风险时明确写出。
- 任何成员都可以处理任何人的 Issue；创建者不拥有排他的认领或实现权限。
- 任务负责人、参与者和审阅者可在协作过程中确定，不要求创建 Issue 时预先指定。
- 多个任务存在明显依赖或需要统一推进时，再建立协作计划；不为单项任务额外维护重复计划。

## 共同变更

- 涉及公共接口、数据模型、架构或兼容性的重要变更，先讨论影响范围和方案，再实施。
- PR 描述应说明修改内容、影响面、验证结果及剩余事项。
- PR 作者必须自审并记录；默认只合并自己提交的 PR，不合并其他成员的 PR。Issue 可跨创建者处理；处理他人的 Issue 不意味着可以合并其 PR。
- 自审不能替代必需 CI、分支保护或已确认的架构决策。
- 发现设计或实现与已确认 ADR 不一致时，先讨论是否需要更新决策，不直接绕过决策。

Git 分支、提交、PR、自审和合并的具体操作要求见 [CONTRIBUTING.md](../../CONTRIBUTING.md) 与 [development.md](development.md)。
